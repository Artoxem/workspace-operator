# Подтверждение destructive-действий человеком

Workspace Operator оставляет destructive-инструменты агенту, но сервер не
выполняет их без подтверждения человека.

Это серверный шлюз, а не просьба в промпте: агент может попросить удалить, но
не может сам подтвердить запрос.

## Как это работает

1. Агент вызывает destructive-инструмент:

   ```json
   {"name": "drive_trash", "arguments": {"file_id": "..."}}
   ```

2. Если клиент поддерживает MCP elicitation, сервер спрашивает человека в UI
клиента: **Подтвердить действие?** Accept выполняет его один раз, decline
отменяет.

   Если клиент не поддерживает elicitation, сервер **ничего не меняет** и
   возвращает обычный результат с `approval_id`:

   ```text
   ⚠️ APPROVAL REQUIRED — the action has NOT run.
   {"status": "approval_required", "approval_id": "apr_…", ...}
   ```

3. Решение принимает оператор вне чата: в CLI или на странице в браузере (см.
   ниже). В результат, который видит агент, не попадают ни команды, ни ссылка,
   поэтому сам он вызов не освободит.

   ```bash
   workspace-operator approvals list
   workspace-operator approvals show apr_…
   workspace-operator approvals approve apr_…
   # или отклонить
   workspace-operator approvals deny apr_…
   ```

4. Агент повторяет **тот же** вызов с `approval_id`:

   ```json
   {"name": "drive_trash", "arguments": {
     "file_id": "...",
     "approval_id": "apr_…"
   }}
   ```

5. Сервер проверяет и расходует approval, затем выполняет действие один раз.

Успех, pending, deny, expiry, повторное использование и несовпадение аргументов
возвращаются как обычные tool-результаты с инструкцией. MCP-сессия не падает.
Ссылка для решения уходит в лог сервера (консоль оператора), а не в tool-результат.

## Привязка и срок

Approval привязан к:

- имени инструмента;
- `action` для консолидированных инструментов;
- SHA-256 хешу всех аргументов, кроме `approval_id` и `confirm`;
- времени истечения (по умолчанию 15 минут, `approval_ttl`).

Изменение `file_id`, `plan_id`, диапазона или любого другого аргумента
аннулирует approval. Он одноразовый: после выполнения id нельзя использовать
снова.

`confirm=true` остаётся флагом намерения, но сам по себе не достаточен:
действие освобождает именно подтверждение человека.

## CLI

```bash
workspace-operator approvals list          # ожидающие запросы
workspace-operator approvals show apr_…    # детали запроса
workspace-operator approvals link apr_…    # ссылка для браузера (содержит секрет)
workspace-operator approvals approve apr_… # разрешить конкретный вызов
workspace-operator approvals deny apr_…    # заблокировать
```

Хранилище подтверждений по умолчанию лежит в `~/.google/approvals`, то есть в той же
папке, что и токен. CLI находит его из любой текущей папки, а контейнер получает
эту папку через монтирование учётных данных, поэтому CLI на хосте и контейнер видят
одни и те же запросы:

```bash
workspace-operator approvals list
```

Или внутри контейнера:

```bash
docker compose exec workspace-operator workspace-operator approvals list
```

## Конфигурация

```yaml
# approval_dir: "~/.google/approvals"  # необязательно; это значение по умолчанию
approval_ttl: 900               # секунды
approval_url: "http://127.0.0.1:8765"  # база для браузерной страницы
```

Переменные: `MCP_APPROVAL_DIR`, `MCP_APPROVAL_TTL`, `MCP_APPROVAL_URL`. Задавайте
`approval_dir` только чтобы перенести очередь, и указывайте абсолютный путь:
относительный отсчитывается от текущей папки.

## Автоматическое открытие браузера

Для HTTP-сервера задайте `MCP_APPROVAL_BROWSER_WAIT=45` (в Docker Compose можно
указать в `.env`). На компьютере оператора, **вне контейнера**, запустите
`workspace-operator approvals watch` и оставьте команду работающей. Ей нужен доступ
к той же очереди; при нестандартном адресе страницы используйте `--url BASE_URL`.
Помощник открывает новые запросы, а не уже существовавшие при запуске. Пока вызов
ожидает, кнопка Approve позволяет ему продолжиться, Deny останавливает его. Если
время ожидания вышло, сообщите решение агенту после выбора в браузере. Ссылка для
автоматического открытия не передаётся MCP-клиенту и не пишется сервером в лог.

## Что показывается при переносе и загрузке в Drive

- **Перенос**: в `bulk_plan` укажите `domain=drive`, `action=move`, `selector.ids`
  (даже если файл один) и `options.target_folder_id`. После проверки плана вызовите
  `bulk_run`. На странице видны папка назначения и **все файлы** с исходными
  папками. Прямого одиночного переноса больше нет.
- **Загрузка**: используйте `drive_write` с `action=upload` и `local_path`. На
  странице видны локальный источник, имя, формат результата, размер и папка
  назначения (корень «Моего диска», если папка не задана). До отправки сервер
  повторно проверяет утверждённое содержимое. Лимит — 100 МиБ на файл.
- Полный предпросмотр доступен в браузере или через `workspace-operator approvals
  show <id>`, а агент получает только краткий статус. Этот предпросмотр не
  заменяется диалогом MCP elicitation. Если вызов уже перестал ждать решения,
  повторяйте его только после подтверждения; если данные изменились, подтвердите
  новый запрос.
- Страница сделана компактно, в терминальном стиле: строка-сводка, затем по одной
  сворачиваемой группе на исходную папку с количеством и суммарным размером. В
  группе первые десять имён; ссылка **show all N files** открывает полный список
  постранично (по 100). ID файлов на странице не показываются — **download CSV**
  выгружает полный манифест (имя, id, исходные папки, назначение, размер, тип).
  Короткий отпечаток на странице и в CSV указывает, какой именно предпросмотр
  будет выполнен.
- Общие диски включаются через `MCP_BULK_ALLOW_SHARED_DRIVES=1`. Перенос возможен
  внутри «Моего диска» или внутри одного общего диска при наличии прав. Перенос
  между дисками и перенос дерева папок не поддерживаются. Чтобы отменить перенос,
  возьмите `previous_parents` из `bulk_result` и составьте новые планы.

## Браузерная страница

Страница необязательна и работает только в HTTP-режиме. У каждого одобрения есть
случайный **секрет**; на диске хранится только его хеш. Агент секрет не видит:
в ответе инструмента приходит `approval_id` и никакой ссылки. Человек получает
ссылку локально:

```bash
workspace-operator approvals link apr_…
# http://127.0.0.1:8765/approvals/apr_…?k=<секрет>
```

И страница, и POST «Approve/Deny» требуют секрет (сравнение за постоянное время).
POST дополнительно отклоняется, если заголовок `Origin` не совпадает с `Host`
(защита от CSRF); страницы отдаются с `no-store`, `Referrer-Policy: no-referrer`,
строгой CSP и `X-Frame-Options: DENY`. Неизвестный id и неверный секрет получают
одинаковый ответ 404. После подтверждения вернитесь в чат и попросите агента
повторить вызов с `approval_id`.

Без секрета агент, знающий `approval_id` и адрес сервера, не может одобрить свой
запрос по HTTP. Не открывайте HTTP-сервер в недоверенную сеть без TLS-прокси:
секрет передаётся в URL.

## Что требует подтверждения

`confirm=true` + approval человека применяются к:

`drive_trash`, `drive_permissions`, `docs_edit`, `sheets_delete`,
`gmail_delete`, `calendar_delete`, `script_run`, `bulk_run`, `bulk_undo`.
`drive_write` → `upload` тоже требует подтверждения человека, но без `confirm=true`.

Чтение, обычная запись, черновики и `dry_run` не требуют approval.
`bulk_plan` всегда dry-run; подтверждение запрашивается при `bulk_run`.

## Модель угроз

Approval защищает от самостоятельных действий агента через MCP. Он не защищает
от агента с произвольным локальным shell вне MCP, который может читать каталог
одобрений (`~/.google/approvals/*.json` содержит секреты), и от человека, который
подтверждает запрос не читая summary. Держите каталог approvals локальным,
запускайте CLI от того же пользователя, что и сервер, и не открывайте MCP
эндпоинт недоверенным пользователям.
